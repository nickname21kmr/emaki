## 0. 要解决什么

每个人想看的页面、想要的默认值、想加的功能都不一样。这一阶段**不做具体的功能**，只做让这些需求能实现的基础能力。拿下面几个例子检验（第 11 节逐个对照）：

| 例子 | 属于哪层 |
| --- | --- |
| 全局排序：原来默认按入库时间，想改成按修改时间；启用就生效，停用就回到原来的默认 | 第 1 层：覆盖插件（只有配置，没有代码） |
| 不常用的页面（比如别册）停用，就看不到这一页 | 内置插件：原来的每一页本身就是一个插件 |
| 统计页：让 AI 助手做一个「各作品收藏的变化」页面，可以启用、停用、改名、删除 | 第 2 层：自己画界面的扩展（2b） |
| 内置的 Pixiv 浏览：浏览排行、关注、搜索，像浏览器下载插件那样批量下载进图库 | 2b（界面）+ 2c（服务端联网、下载、后台任务） |
| 页面编辑模式：按住 Ctrl 点任意一个页面元素，把它引用给 AI | 基础能力（这一阶段不做，但要留好接口，第 10 节） |

## 1. 已经定下的

| # | 问题 | 决定 |
| --- | --- | --- |
| 1 | 插件来源和信任 | 只装本地的文件、文件夹或 git 地址；装之前列出它要的全部权限；不做签名，不做公开的插件市场 |
| 2 | 插件的权限上限 | 默认什么都不能做，按权限范围逐项授权；联网要逐个列出域名 |
| 3 | AI 生成的页面 | 只读的直接能用；会改数据的，保存时就把权限一起授权（见原则 2，不再单独「第一次使用时确认」） |
| 4 | 对齐 MCP Apps | 对齐。锁定 2026-01-26 的稳定版协议，在外面包一层薄封装；规范再变，只改这一层 |
| 5 | 第 3 层逃生口 | 要做。自动停用按「它改的点变了」，不按 Emaki 的版本号（2026-11-27 定，第 7 节） |
| 6 | 维护者设计的页面 | 原来的页面变成内置插件，**看起来、用起来和现在没有区别**；底层怎么变都行，就像 Windows 开了虚拟化以后，系统本体也跑在虚拟机里，但用的人感觉不到 |
| 7 | 权限要多严 | 不追求严苛：这是自己用的，不做插件市场，别人的插件出了问题后果自负。遇到解决不了的阻碍可以放宽。所以 2c 用 Node 子进程，不用 QuickJS（第 3 节） |
| 8 | AI 做的页面的权限上限 | 不超过助手自己的范围（5.1） |
| 9 | 个人状态存在哪 | 哪些插件启用、改过的名字这类状态跟着图库走，电脑和手机共用一份；手机上想不一样，再单独存一层本机的差异（第 9 节） |
| 10 | 怎么个性化 | **一切都是插件**：原来的页面是内置插件，改默认值是覆盖插件，AI 做的页面、装的功能也是插件，全在一个「插件」页里启用、停用、重命名、删除（第 9 节）。不做在页面上拖来拖去的编辑 |
| 11 | 叫法 | 统一叫「插件」，不叫 mod；第 3 层的插件挂一个小签「改内部」 |
| 12 | 页面顺序 | 侧栏（手机上是底部标签栏）的页面顺序可以调（9.6） |

| 14 | 「一切都是插件」到哪一层 | 只有**管理**是统一的；页面、覆盖、按钮各有各的代码，按「贡献点」分开实现（9.1–9.3） |

## 2. 原则

1. **一切都是插件，内置的也走同一套。** 原来的每一页都是一个内置插件，能停用；改默认值是一个覆盖插件，启用就生效、停用就还原；AI 做的页面、装的功能也是插件。它们全在一个地方管（第 9 节）。原来的页面、看图器的按钮、信息栏的栏目、后台任务，全部通过插件用的那套注册接口登记。好处有两个：一是接口够不够用，内置功能自己先验证过；二是同一个行为只有一处实现，插件要改也只改这一处。用户感觉不到任何变化（决定 6）。
2. **一次授权，用的时候不再问。** 一个插件（或者 AI 做的一个页面）在装上或保存时，用**一张单子**列出它会做的所有事：读什么、改什么、连哪些网站、往哪个文件夹写、会不会在后台跑、会不会改内部。点一次「允许并启用」就全部生效。用的时候不再弹任何确认；越界的调用直接失败，不弹窗问你。只有更新时要了**新的**权限，才再出一张单子，而且只列新增的那几项。
3. **隔离第一天就定。** 插件按「代码在哪跑」分成几档（第 3 节），档位决定它碰得到什么。不先把内部对象全交出去再事后收紧：Obsidian、Grafana 都证明了，事后收紧收不回来。
4. **隐私承诺不变，说法要老实。** 视图（2b）默认不能联网，这一点由浏览器强制执行。服务端逻辑（2c）要连哪些网站必须在清单里声明，但 Emaki 不强制拦截（决定 7），授权单上就照实写「声明会连接」。一个插件如果既能读原图、又能联网，授权单上直接写「可能把图片发到 某某网站」，不让人自己去拼这两项意味着什么。
5. **你的决定优先。** 配置按「内置 → 插件 → 你」的顺序合并，你的永远最后生效。插件改的数据和 AI 助手一样：记下是谁改的，能撤销。插件默认和助手一样，不能移动、删除文件。
6. **坏了能恢复，升级不炸。** 一个插件坏了只影响它自己那一块；有安全模式；插件声明兼容哪些版本，不兼容就自动停用并写明原因。
7. **一个行为一个实现。** 插件只碰登记过的扩展点。第 3 层能改内部，但改的也是登记过名字的内部点（第 7 节）。

## 3. 分层和运行方式

三层还是 core-architecture 第 10.2 节那三层；第 2 层按「代码在哪跑」再细分成三档。**一个插件是一个包，可以同时包含好几层的内容，授权只有一次。**

| 层 | 内容 | 代码在哪跑 | 碰得到什么 |
| --- | --- | --- | --- |
| 1 覆盖 | 只含配置的插件：改设置注册表里登记过的值（默认排序、主题、快捷键、阈值；以后也包括区块的显示和顺序） | 不跑代码，只是数据 | 只能改登记过的值 |
| 2a 声明式贡献 | 导航项、看图器按钮、菜单项、页头操作、命令面板项 | 不跑代码：写在清单里，点了执行某个命令或打开某个视图 | 绑定的命令（受授权限制） |
| 2b 视图 | 整页、区块、信息栏栏目、统计页 | 隔离的 iframe（MCP Apps 格式，第 5 节） | 只能通过桥接调用授权范围内的命令和查询 |
| 2c 服务端逻辑 | 插件自己的命令、后台任务种类、对变化的反应、证据来源、联网抓取 | 每个插件一个 Node 子进程（第 6 节） | 图库数据只能通过宿主接口（命令和查询，受授权限制）；文件只能读写自己的目录（Node 权限模型强制）；联网按声明，不强制拦截；能用 npm 包 |
| 3 逃生口 | 改内部实现 | 和 Emaki 同一个进程：服务端是 Node 模块，网页是同一个页面里的模块 | 能做 Emaki 能做的一切；只改登记过名字的内部点，改的点变了就自动停用（第 7 节） |

另外还有**外部程序**：任何语言写的程序，拿一张带权限范围的凭证，通过 HTTP 或 MCP 访问。手机 App、外部 AI Agent 现在就是这样接进来的。它们不算插件，但和插件共用同一套授权（第 4 节）。

**为什么 2c 用 Node 子进程**：Node 的权限模型能管文件、子进程、worker，**管不了网络**（本机 Node 22 和 24 都没有网络开关，已核对）。要让「只能连声明过的网站」真的生效，就得换成 QuickJS 这类本身不能联网的沙箱，代价是插件不能用 npm 包、宿主要多做一整套桥接。按决定 7 不追求这么严，所以用 Node 子进程：插件能用 npm 包；崩了不会带垮 Emaki；读写文件被限制在自己的目录里（这一条是强制的）；图库数据只能通过宿主接口拿（插件进程拿不到数据库的路径和凭证）。联网照声明列在授权单上，但不拦截。以后真要严格，再给 2c 加一档 QuickJS 沙箱，清单格式不用变。

**识别模型这类重计算**不放进 2c：新的识别模型做成「模型包」，包括模型文件、标签表和阈值，属于第 1 层的数据，由 Emaki 现有的推理引擎来跑。

## 4. 授权

### 4.1 一个模型

设备、AI 助手、外部程序、插件，都是「被授权的对象」，授权的内容是同一种 `Grant`：

```ts
interface Grant {
  scopes: Scope[];                 // 命令 / 查询的权限范围（packages/shared/src/commands.ts，按需要加新的）
  folders: FolderGrant[];          // 能往哪个图库文件夹放文件（手机上传的目标文件夹就是这个）
  network: string[];               // 声明会连的域名（只有插件有；2b 视图由浏览器强制，2c 按声明、不拦截）
  background: boolean;             // 能不能在后台跑（任务、对变化的反应）
  unsafe: boolean;                 // 第 3 层：改内部
}
```

- **检查只有一处**：服务端的 `authorize(谁, 要做什么)`。命令、查询、文件夹、联网都经过它，前端只根据授权决定显示哪些入口。
- **叠加取交集**：在手机上用插件，生效的权限是「插件的授权 ∩ 这台设备的授权」。Claude 里打开插件的页面，生效的是「插件的授权 ∩ 这个 MCP 客户端的授权」。哪一方都不会因为另一方而多出权限。
- **入口按能力显示**：插件贡献的按钮、菜单，和现在一样按能力显示（`lib/capabilities.ts`），生效权限里没有对应范围就不显示。
- **记录是谁改的**：actor 记成 `plugin:<id>@<版本>`，进审计记录，能撤销，在顶栏的撤销栈里标「插件名：」。
- **存储**：设备的授权仍然在 `devices` 表里（已经有 `scopes`、`upload_root_id`），由 `access/` 写；插件的授权在 `plugin_grants` 表里，由插件模块（`domain/plugins/`）写——装、更新、卸载要和清单、启用状态在同一个事务里，一起撤销（E2 定的，见 12.3）。两边都转成同一个 `Grant` 类型（`@emaki/shared`）。

### 4.2 一张授权单

装插件、启用插件、保存 AI 做的页面，都弹同一张单子（`GrantSheet`）。权限用人话写，危险的标朱色，需要选的东西也在这张单子里选好：

```
Pixiv 浏览  0.1.0                                      来自：本地文件 pixiv-browser-0.1.0.zip
──────────────────────────────────────────────────────────────
它会：
  · 读你的图库（列表、详情、计数）
  · 把下载的图加进图库，放在  [ 下载图片 / Pixiv  ▾ ]      ← 就在这里选，之后不再问
  · 连接 www.pixiv.net、app-api.pixiv.net、i.pximg.net（插件声明的）
  · 在后台下载（任务列表里能看到、能取消）
它不会：移动或删除你的图、改设置、把你的图发出去
──────────────────────────────────────────────────────────────
                                   [ 取消 ]   [ 允许并启用 ]
```

- 单子上的话由宿主根据清单生成，插件自己写不了，避免话术误导。权限组合起来有风险时（比如既读原图又联网），宿主直接写出后果。
- 第 3 层插件的单子单独一种样式：改的每一处一行、朱色（「改 Emaki 内部的『排名的张数怎么数』」），再写明「在 Emaki 自己的进程里运行它的代码：不隔离，可以做 Emaki 能做的任何事；Emaki 更新后它改的地方变了，它会自动停用，等你确认」，不写「它不会」。
- 插件的授权在「插件」页的详情里看、改（9.7）；设备和 AI 助手的授权仍在各自的设置页，用的是同一个单子组件。

## 5. 视图（2b）：Emaki 当 MCP Apps 的宿主

- **格式**：视图是 MCP Apps 的 `ui://` HTML 资源（`text/html;profile=mcp-app`），协议锁定 2026-01-26 稳定版。视图那边用官方的 `App` 类。
- **在 Emaki 里**：网页用 iframe 显示视图。iframe 只开 `allow-scripts`，不开 `allow-same-origin`，所以每个视图都是独立的匿名来源，碰不到 Emaki 页面的 Cookie 和存储，各视图之间也互相碰不到。安全策略默认不能联网，图片地址只放行宿主给的地址（见下）。
- **数据走桥接**：视图通过 `tools/call` 调用命令和查询。工具清单就是现在给 MCP 生成的那份，再按生效权限过滤，名字也一样（`curation_link`、`read_library` 等）。桥接的宿主端打算用官方 `@modelcontextprotocol/ext-apps` 的 `AppBridge`，把调用接到命令和查询注册表上；它能不能不接 MCP 客户端直接用，要在 E0 验证。
- **Emaki 自己加的方法**：统一加 `emaki/` 前缀、带版本号，包括导航和打开看图器、读写当前选择、插件自己的存储（键值）、订阅变化事件（MCP Apps 不管事件）。在 Claude 里跑时这些方法不存在，视图先检测有没有，没有就退化。
- **图片**：缩略图和原图走宿主发的短期地址（`/api/plugin-media/<令牌>/...`，令牌绑定插件和权限范围），用普通的 `<img>` 加载，不经过桥接拷贝。
- **插件用的库**：官方的 `App` 类（`@modelcontextprotocol/ext-apps` 的 `app-with-deps`，约 540 KB）加上 Emaki 的一层小封装，由宿主在固定地址提供（`/plugin-sdk/app.js`，普通脚本，全局 `Emaki`，E4 定的，见 12.5），插件页面不用各自内联一份。宿主这边的 `AppBridge` 连同依赖约 1 MB（未压缩），只在第一次显示插件页面时按需加载，不进主包。
- **自己跳走**：插件页面可以把自己跳转到外部网址（`location.href = …`），浏览器没有能拦这一下的开关，数据可能借此带出去。宿主监听 iframe 的 `load`：第一次以后再触发就说明跳走了，立刻撤掉这个页面并记一次错误。请求在被发现之前已经发出去了，按决定 7 接受这个残余风险，授权单上不另写。
- **默认关闭的方法**：MCP Apps 里 `ui/message`、`ui/update-model-context` 能直接往 AI 的上下文里写东西，是一条注入通道。默认不开，要用的插件在清单里声明，授权单上写出来。
- **向外**：插件的视图同时作为 Emaki MCP 服务器的工具挂出去，带 `_meta.ui.resourceUri`。在 Claude、ChatGPT 里调用这个工具，对话里就会显示同一个页面，权限取交集（4.1）。
- **性能**：视图只能用分页和统计查询；宿主限制每个插件的调用频率和单次返回的大小；页面上的区块视图滚到可见时才加载。

### 5.1 AI 做的页面

- 助手新增一个权限范围 `plugins`，以及两个工具：`plugins_save_view`（视图的 HTML 加清单）、`plugins_list`。
- **保存就是授权**：助手做好一个页面后，在对话里出一张卡片，内容就是授权单（4.2），外加「在侧栏显示」的选项，点一次就完成。只读的页面，这张卡片就是一个「保存」按钮。
- **权限上限**：AI 做的页面，权限不超过助手自己的范围；要更多，你到「插件」页里自己改。这是为了防止助手被注入以后，借一个页面越权。
- **版本**：每次保存是一个新的、不再修改的版本；页面配置指向当前版本。助手修改页面就是保存新版本，权限没变就不再弹授权单。
- 数据目录里的位置：`data/plugins/ai.<名字>/<版本>/`，不进 Git。

## 6. 服务端逻辑（2c）

- **怎么跑**：每个插件一个 Node 子进程（`child_process.fork`，用 Emaki 自带的那个 Node），启动时加权限参数：只能读插件自己的包目录，只能写插件自己的数据目录。Node 22.13 之前这个开关叫 `--experimental-permission`，启动时先用 `process.allowedNodeEnvironmentFlags` 看认哪个。宿主和插件之间用 IPC 通信，插件拿到一个注入好的 `emaki` 对象：
  - `emaki.call(命令或查询, 输入)`：受授权限制，actor 是这个插件；
  - `emaki.fetch(url, 选项)`：走 Emaki 现有的网络设置（系统代理、Clash 检测），省得插件自己处理代理；插件也可以直接用 Node 的 `fetch`，不拦截；
  - `emaki.storage`（键值）、`emaki.secrets`（登录凭证这类，存在数据目录里，视图读不到）、`emaki.files`（插件自己的临时文件夹）；
  - `emaki.jobs.register(种类, 处理函数)`：后台任务在运行时注册（E3 先把内置任务改成这样登记），任务列表、进度、取消都用现有的；
  - `emaki.on(变化类型, 处理函数)`：订阅变化，只能事后旁观，不能拦下原来的操作；要拦截，走第 3 层。
- **插件的命令**：在清单里登记，名字带插件前缀（`pixiv-browser.download`），输入写 JSON schema，进命令注册表，和内置命令一样能被视图、助手和 HTTP 调用。
- **放文件**：插件不直接写图库文件夹。它把文件下载到自己的临时文件夹，再调用 `library.import`，放进授权里给的那个文件夹；去重、入库、识别都走现有的路。
- **资源限制和崩溃**：限制子进程的内存，单次调用有超时；子进程崩了，按退避时间自动重启，并记一次错误（第 8 节的自动停用按这个计数）。

## 7. 逃生口（第 3 层）

- **形式**：服务端是在 Emaki 进程里加载的 Node 模块（清单的 `internal`），网页是在同一个页面里加载的模块（下一步）。模块导出 `activate(internal)`，拿到：
  - 登记过名字的内部点（`core/points.ts`）：命令和查询的执行函数（`command:<名字>`、`query:<名字>`）、对变化的反应（`reaction:<名字>`）、后台任务的执行体（`job:<种类>`）、
    口径（`term:<名字>`，现在有 `term:count.unit`「排名的张数怎么数」），以后还有网页上登记过的组件和 hook（`patchable('component:lightbox.Stage', …)`）。只登记内置的，插件自己的命令、任务不算；
  - `internal.patch(名字, { before, after, around })`：只能改清单 `patch@1` 里列的点；多个补丁按加上的顺序叠起来，后加的包在外层，不互相覆盖；插件停用时 Emaki 把它的补丁全部撤掉；
  - `internal.engine`：整个引擎，没登记的内部也拿得到，但完全不保证兼容。
- **清单**：`"permissions": { "unsafe": true }`、`"contributes": { "patch@1": [{ "point": "term:count.unit", "why": "…" }] }`、`"internal": "server/patch.mjs"` 三样一起写；
  点在这个版本的 Emaki 里没有就装不上、不能启用。
- **谁改了哪里能查**：「插件」页的「谁改了哪里」列出每个加了补丁的点和改它的插件；插件详情的「改内部」列出它改的每一处现在怎么样（生效中、没在改、Emaki 改过这里、这个版本没有）。
  补丁自己抛的错记在打补丁的插件头上（和别的出错一样，短时间多次就自动停用）。
- **改的点变了才停用**（2026-11-27 定，不按版本号绑定）：每个点有一个指纹——登记的那一层的实现（函数的源码）、输入的格式（命令的 JSON Schema、反应订阅的变化……）和手动的版本号。
  装上、启用时记下它改的点的指纹；Emaki 更新以后对不上，这个插件就不加载、自动停用，通知「它改的『排名的张数怎么数』变了」；你可以一键「仍然启用」（按现在的样子重新记），后果自负。
  没变的照常加载，不会每次更新都停（Emaki 的版本号一直是 0.1.17，按版本号绑等于没绑；按每次部署停又太吵）。指纹只看登记的那一层，更深处（比如命令调用的领域方法）改了看不出来。
  做法和 Minecraft 的 Fabric Mixin 一样：补丁指明改哪个有名字的点，加载时先核对这个点还是不是原来的样子；VS Code 只给公开接口（不能改内部），Obsidian 直接改内部、不核对（升级就悄悄坏）。
- **前提**：内部点能按名字打补丁，靠的就是「一个行为一个实现」。一个行为散在几处，就要补几处，第 7 节就做不成。所以 E3 先把内置功能全部登记好（第 9 节）；
  E6 把排名用的张数收拢成一个口径（`readmodel/terms.ts` 的 `COUNT_UNIT`），角色、作品、画师的张数都从它来。

## 8. 版本、冲突、恢复

- **清单**（`emaki-plugin.json`）：

```json
{
  "id": "pixiv-browser",
  "name": "Pixiv 浏览",
  "version": "0.1.0",
  "engines": { "emaki": ">=0.2 <0.3" },
  "permissions": {
    "scopes": ["read", "import", "jobs"],
    "folders": [{ "id": "downloads", "purpose": "下载的图放在这里", "suggest": "下载图片/Pixiv" }],
    "network": ["www.pixiv.net", "app-api.pixiv.net", "i.pximg.net"],
    "background": true
  },
  "contributes": {
    "nav.item@1": [{ "id": "pixiv", "label": "Pixiv", "page": "browse" }],
    "page@1": [{ "id": "browse", "view": "ui://pixiv-browser/browse.html" }],
    "lightbox.toolbar@1": [{ "id": "open-source", "label": "在 Pixiv 打开", "command": "pixiv-browser.openSource" }],
    "command@1": [{ "name": "pixiv-browser.download", "scope": "import", "input": "schemas/download.json" }],
    "job.kind@1": [{ "kind": "pixiv-browser.download", "label": "下载 Pixiv 作品" }],
    "setting@1": [{ "id": "account", "type": "secret", "label": "Pixiv 登录" }]
  },
  "server": "server/index.js"
}
```

- **扩展点各自带版本号**（`lightbox.toolbar@1`）。宿主同时支持当前版和上一版；实验中的扩展点只在开发模式下能用。插件声明的版本不兼容，就自动停用，并写明是哪一项。
- **冲突**：
  - 追加型的（按钮、菜单、栏目、区块、任务种类、反应）全部共存，按清单里的 `order` 排；不想要哪个，停用那个插件，以后也可以用覆盖调整顺序、藏起单个按钮。
  - 独占型的（默认阅读方式、替换某个区块）检测到冲突时让你选，不悄悄覆盖。
  - 命令、设置、存储都带插件前缀，不会撞名。
- **更新**：不静默自动更新。「检查更新」列出新版本；权限没变就一键更新，权限多了就出授权单，只列新增的那几项。
- **坏了**：
  - 每个视图、区块各自包一层错误处理，坏了只显示一张错误卡，卡上有「停用这个插件」；
  - 一个插件短时间内出错多次就自动停用，并发一条通知；
  - 服务端加载插件时连续崩溃，下次启动自动进入安全模式，并退回上一份正常的配置。
- **安全模式**：只用内置插件，全部按原来的样子启用，「我的」和「装的」插件全部不加载，覆盖全部不生效。入口有三个：
  - 启动时加 `--safe`；
  - 网址加 `?safe`；
  - 安卓 App 原生设置页里的开关：网页本身坏了也能进去。
- **卸载**：插件自己的存储、凭证、临时文件、授权一起删掉；它导入的图和改过的数据留着（那是你的图库）。

## 9. 一切都是插件：怎么抽象

在用的人看来，一个页面、一个覆盖设置、一个 Pixiv 下载功能都是「插件」，都能启用、停用、改名、删除。可它们实际上不可能用同一份代码：页面要渲染、要占路由；覆盖是一个值；下载功能是一个子进程。所以「一切都是插件」只在最上面那一层成立，往下分三层，三层互相独立：

```
① 插件管理（统一，只有一份）
   包、身份、来源、版本、启用 / 停用、显示名、删除、授权、出错计数、安全模式
   它不知道页面、覆盖是什么；输出只有一样：「现在生效的贡献清单」
        │  只收启用了的、授权够的、版本兼容的插件的贡献
        ▼
② 贡献点（每种一份，各管各的）
   page、nav.item、override、block、lightbox.toolbar、menu.item、command、job.kind、reaction、setting、patch …
   每种有自己的 schema、版本号、合并和冲突规则、用户能调的状态（比如导航顺序）
        │  贡献里写的「怎么跑」
        ▼
③ 运行方式（按代码在哪跑，第 3 节）
   内置组件（同进程，只给内置插件）、iframe 视图（2b）、Node 子进程（2c）、同进程补丁（第 3 层）
```

- **插件只是一个包**：清单里列出它贡献了哪些东西。插件管理只管包本身的事。
- **每个贡献点是一个注册表**：只收「生效的贡献清单」里属于自己的那部分，不知道插件是怎么装、怎么启用的。现在已经有的区块注册表 `blocks/registry.ts`、页面表 `pages.ts`、命令注册表，都会变成贡献点。
- **用户看到的「类型」是推出来的，不另存**：只有 `override` 的插件显示为「覆盖」，有 `page` 的显示为「页面」，有服务端代码的显示为「功能」，有 `patch` 的挂「改内部」小签。一个插件同时有好几样，就显示主要的那一样，其余挂小签。
- **状态各归各的主人**（单一写入者）：启用、显示名、授权归插件管理；导航顺序归 `nav.item`；覆盖冲突时选了哪个归 `override`。插件被删掉时，各贡献点把属于它的状态一起清掉。

### 9.1 插件管理（统一的部分）

| 管什么 | 说明 |
| --- | --- |
| 身份 | `id`（不变）、名字、显示名（你改的名字）、来源（内置 / 我的 / 装的）、版本 |
| 状态 | 启用或停用；必需的内置插件（设置、「插件」页）不能停用。看图器、阅读器是必备的内置功能，不拆成单独的插件（2026-11-27 定：拆出来对用的人没有意义，停用了也没法看图）；阅读器属于「合集」，看图器不属于哪个插件。它们里面的按钮、栏目、阅读方式已经按贡献点登记（E3），插件往里加东西、停用插件时它的条目不画，都照常 |
| 生命周期 | 安装、更新、删除；内置插件只能停用，不能删 |
| 授权 | 第 4 节的 `Grant`、授权单 |
| 健康 | 出错计数、自动停用、安全模式（第 8 节） |
| 输出 | 生效的贡献清单：服务端算好，网页和服务端各自的贡献点都从这里取；变了推一条事件，网页按事件刷新 |

### 9.2 贡献点（各管各的）

| 贡献点 | 谁来实现 | 多个插件一起贡献时 | 你能调的 |
| --- | --- | --- | --- |
| `page` | 路由和渲染：内置组件，或者 iframe 视图（第 5 节） | 路由带插件前缀，不撞 | — |
| `nav.item` | 侧栏、手机底部标签栏 | 都排进去 | 顺序、在不在侧栏显示、显示名（9.6） |
| `override` | 设置注册表算出每个值的生效值（9.5） | 同一个值有冲突时你来选 | 冲突时选哪个 |
| `block` | 页面里的区块（`PageBlocks`） | 都排进去，按 `order` | 以后用覆盖调整 |
| `lightbox.toolbar`、`lightbox.panel`、`menu.item`、`page.action` | 看图器、菜单、页头 | 都排进去 | 以后用覆盖调整 |
| `link` | 接管的链接（12.7）：图片的来源这类外部链接在插件里打开 | 独占：几个插件都接管同一个链接时点了让你选 | — |
| `command`、`job.kind`、`reaction` | 命令注册表、后台任务、变化订阅（服务端） | 名字带插件前缀，不撞 | — |
| `setting` | 插件自己的设置，宿主统一画 | 带插件前缀 | 在插件详情里改 |
| `patch` | 第 3 层（第 7 节） | 按加载顺序叠起来 | 看「改了哪些内部点」 |

新加一种贡献点，就是新加一个注册表加一份 schema，插件管理不用动。每种贡献点单独带版本号（第 8 节）。

### 9.3 运行方式

见第 3 节。同一种贡献点可以有几种跑法，比如 `page` 可以是内置组件，也可以是 iframe 视图。内置的页面用内置组件，所以和现在一样快、一样的样子（决定 6）；插件的页面用 iframe 视图。

### 9.4 停用内置的页面

- **只影响界面**：导航里没有这一页了，别处通往它的入口也一起藏起来（比如首页的「别册目次」、命令面板里的项）；直接打开地址，显示「这一页已停用」和「去启用」。
- **不改数据，不停后台**：别册照样分类，识别照样跑。重新启用，一切照旧。
- **不另写一套**：现在已经能按权限把整页、设置分节、操作藏起来（`pages.ts`、`lib/capabilities.ts`，docs/mobile.md 4.4），停用就是在同一个判断里多一个条件。
- **登记拥有关系**：每个内置插件登记它拥有的路由、导航项，以及在别的页面里的区块和入口。拥有关系写清楚，停用了才不会留下死链接。这和 E3 给看图器按钮、菜单项建注册表是同一件事。

### 9.5 覆盖插件（第 1 层）

只含配置、不含代码的插件：

```json
{ "id": "my.sort-by-mtime", "name": "默认按修改时间排序", "version": "1",
  "contributes": { "override@1": { "images.defaultSort": "modifiedAt" } } }
```

- **能覆盖什么，由设置注册表决定**：每个可覆盖的值登记 id、schema、内置默认值、作用范围（图库 / 本机）。
  - 第一个是 `images.defaultSort`。现在「默认按入库时间」写死在 4 处：网页图库、角色页的筛选、服务端 `listImages`、`collapsedImages`。改成都读这一个值以后，网页、手机、AI 助手的默认排序就一致了；各页面上的排序控件照旧。
- **启用就生效，停用就回到内置默认**，不用记原来是什么。
- **生效顺序**：内置默认 → 启用的插件的覆盖 → 设置页里你直接改的值。设置页上被插件覆盖的项，写一句「由插件「默认按修改时间排序」设定」。
- **冲突**：两个启用的插件覆盖同一个值，「插件」页标出「冲突」，让你选用哪个；选之前，按后启用的那个。
- **怎么做出来**：
  1. 让 AI 助手做：说一句「默认按修改时间排」，它生成这个插件，对话里出一张卡片，点「启用」；
  2. 「插件」页的「新建覆盖」：从可覆盖的值里选一项、填值、起名；
  3. 别人给的文件。
- 以后区块的隐藏和顺序也可以做成覆盖（比如 `page.home.blocks`），不需要另一种机制。
- 覆盖插件和别的插件是同一种包，只是它只贡献了 `override`；所以它也在「插件」页里启用、停用、改名、删除，不用另做一套管理。

### 9.6 页面顺序

- 侧栏的页面顺序可以调；手机竖屏的底部标签栏用同一个顺序，排在前面的几个直接放在标签栏上，其余进「更多」。
- **启用和「在侧栏显示」是两回事**：停用一个页面插件，这一页就没了（9.4）；页面还在、只是不放进侧栏，它仍然能从别的页面的链接、命令面板打开。「插件」页自己就是这样：必需、不能停用，但默认不在侧栏里（9.7）。
- 顺序和「在侧栏显示」存在 `nav.item` 自己的状态里（按导航项的 id 记，跟着图库走），不存在插件管理里。新启用的页面插件默认显示，排在最后。
- 在哪调：「插件」页的「页面顺序」视图里按住把手拖动（鼠标、触屏都行），或者用「上移 / 下移」（键盘、读屏也能用）。侧栏上右键（触屏上长按）有「调整页面顺序…」，直接跳过去。
- 改名也在这里：页面的显示名会同时改导航项和页头标题，内置页面可以「恢复原名」。

### 9.7 「插件」页

插件可能很多，单独一页 `/plugins`，不塞进设置。它本身是一个必需的内置插件，不能停用。

- **入口**：
  - 默认**不在侧栏里**。设置里有一节「插件」，只放最基本的：开关「在侧栏显示『插件』」，和一个「管理插件…」链接，点了进 `/plugins`。
  - 打开开关以后，它就和别的页面一样出现在侧栏里（手机上在「更多」里），可以调位置。
  - 命令面板也能直接进；侧栏右键的「调整页面顺序…」也会进到这里。
  - 手机等设备：这一页能看（read）就能打开，但只读——启用、停用、改名、删除、调顺序要 `plugins`，安装要 `install-plugins`，没有的按钮不出现、开关是灰的。两个都没有的设备在这里什么都改不了，侧栏、「更多」、命令面板里不放「插件」，侧栏长按也不弹「调整页面顺序…」（没有 `plugins` 就不弹）；直接打开地址照常能看（用户 2026-11-26，`apps/web/src/pages.ts` 的 `entry`）。
- **「页面」视图**：按侧栏的顺序列出所有启用着的页面（内置的、插件的），每一行有拖动把手、「在侧栏显示」、显示名。侧栏和底部标签栏就是在这里编排的。停用的页面不在这里，到「全部」里去启用。
- **「全部」视图**：所有插件。
  - 有搜索框，可以按类型（页面 / 覆盖 / 功能）、来源（内置 / 我的 / 装的）、状态（启用 / 停用 / 出错 / 冲突）筛选；
  - 每一行：名字、类型和小签、启用开关、「⋯」（重命名、删除）；
  - 点一行打开详情 `/plugins/:id`：它贡献了什么（按贡献点列出）、它自己的设置、授权单、版本和更新、出错记录、改了哪些内部点。
- **底部**：安装（文件、文件夹或 git 地址）、新建覆盖、安全模式。
- 启用、停用、改名、删除、调顺序都即时生效，可以撤销（进撤销栈）。删除装的插件，会删掉它的包、存储、凭证和授权；它导入的图和改过的数据留着。
- 这些状态跟着图库走，电脑和手机共用（决定 9）。

### 9.8 叫法

界面上统一叫「插件」，不叫 mod（决定 11）。代码和文档里也统一叫插件（`plugins/`、`emaki-plugin.json`）。

## 10. 留好的接口：页面编辑模式

这一阶段不做「Ctrl + 点击引用给 AI」，但先定好一条规矩：**每个区块、每个显示实体（图、角色、作品、合集）的元素都带 `data-emaki-ref`**，值是 `{类型, id}`，例如 `block:home.stats`、`image:123`。区块已经有稳定 id，实体都有 id，这条规矩用测试检查。以后做编辑模式，只需要把选中的 ref 像现在的「图片选择」一样放进助手的上下文。插件视图里的元素由插件自己报 ref（通过 `emaki/` 前缀的方法）。

## 11. 例子怎么落到基础能力上

| 例子 | 用到的能力 | 在哪个阶段能做 |

### 12.1 E0 的结论（2026-11-24）

四项都能用，方案不用换。

| 验证项 | 结果 |
| --- | --- |
| ① 隔离的 iframe | `sandbox="allow-scripts"` 加 `srcdoc`，安全策略写在插件页面的 `<meta>` 里。电脑 Chromium、安卓 Chrome 124、安卓 WebView 124（模拟器上一个最小的 WebView App）三处结果一样：插件页面的来源是 `null`，本地存储、Cookie、宿主页面的 DOM 都碰不到（`SecurityError`），直接请求宿主接口和外网都被安全策略拦下 |
| ② 官方宿主库接我们的注册表 | `@modelcontextprotocol/ext-apps` 2.0.4（MIT）的 `AppBridge` 第一个参数传 `null`，不接 MCP 客户端，用 `oncalltool`、`onreadresource` 接到自己的处理函数上；插件页面用官方 `App` 类 `callServerTool` 调到了宿主，握手几毫秒。它依赖 MCP SDK 2 的 `client`、`core` 和 zod 4：只在网页这边用，和服务端现在的 SDK 1.32 不冲突，zod 版本和仓库一致 |

| ④ 插件页面里的图片 | 宿主给的地址用普通 `<img>` 加载正常（安全策略只放行宿主地址）。匿名来源的请求不带 Cookie，所以插件图片必须走地址里带短期令牌的方式（第 5 节），局域网入口靠 Cookie 登录的 App 里也成立 |

另外查到的：插件页面能自己跳到外部网址把数据带出去，宿主能在事后发现（iframe 第二次 `load`），处理办法写在第 5 节。HTTPS 自签证书下 iframe 里的图片走的是 App 已经认过的那张证书，E4 在平板上实测时再确认一遍。

### 12.2 E1 做了什么（2026-11-24）

- **服务端**（`domain/plugins/`，迁移 052）：插件管理只有一份——启用、停用、改名、删除、新建覆盖、改值、冲突时选哪个、侧栏布局；
  都走 `ctx.mutate`，能撤销，声明 `plugins.changed`。生效的结果由 `@emaki/shared` 的 `resolvePlugins` 算（网页没取到时用同一个函数算内置的默认，所以不闪）。
  新权限范围 `plugins`：AI 助手和设备默认都有（MCP 快照只多了 7 个插件工具）。`--safe` / `EMAKI_SAFE=1` 是服务端的安全模式。
- **图片的默认排序**：`images.list` 没给排序时按生效值（按姿势筛选时照旧按典型度）；网页的图库、别册、角色和作品页的筛选从 `useOverride` 取。
  「没给就当 addedAt」的写法原来有 4 处，现在源码里一处都没有（`lib/plugins.test.ts` 扫源码）。
- **网页**：侧栏和手机底部标签栏按插件的顺序（前四个常驻，「原创」这种捷径不算）；停用的页面不能去（`canVisit`），直接打开显示「这一页已停用」，
  能改插件的可以直接点「启用」；首页停用了，「/」去侧栏里第一个能去的页面；属于停用插件的区块（首页的别册目次）不画；
  别处去别册的链接和「另有 N 张在别册」这类说法跟着收起（说明文字不改）。改名改侧栏、底部标签栏和列表页的页头标题（`PageHeader` 的 `nav`）。
- **「插件」页** `/plugins`（全部 / 页面顺序两个视图）、详情 `/plugins/:id`、新建覆盖、改名、删除；设置里「插件」一节（排在「关于」前面）；侧栏右键「调整页面顺序…」；
  地址带 `?safe` 是网页这一半的安全模式（这个标签页一直有效，`?safe=0` 退出）。
- **和计划不一样的地方**：
  - 页面顺序先只做了「上移 / 下移」（到一段的头尾就挪到相邻那一段）。拖动后来补上了（2026-11-27，`lib/useDragSort.ts`，没引入拖放库）：
    按住每一行左边的把手拖，鼠标、触屏都行，别的行实时让位，能拖到别的一段，靠近上下边自动滚，Esc 放回去；上移下移留着给键盘和读屏。
  - `data-emaki-ref` 的规矩没在 E1 做：给每个区块和实体加标记要动很多组件，又只有编辑模式用得上，挪到做编辑模式的时候一起做（第 10 节）。
  - 「必需」只剩设置和「插件」页：看图器、阅读器是必备的内置功能，不拆成单独的插件（2026-11-27 定，见 9.1）。
- **验收**：服务端 `test/plugins/plugins.test.ts` 14 个、路由冒烟 8 个；网页 `lib/plugins.test.ts` 7 个、`pages.test.tsx` 跟着改；
  演示数据上逐页截图（电脑 1440×900、手机 390×844，23 张）：除了设置页目录多了「插件」一项，其余和改前逐像素一致（首页 7 天柱状图、图库一行淡入的差异改前两次重拍也有）；
  浏览器走查 20 项全过（停用 / 启用别册、新建覆盖后图库默认按修改时间、地址里不写默认排序、调顺序后侧栏和手机标签栏一起变、改名和撤销、设置里的开关、右键菜单、安全模式）。

### 12.3 E2 做了什么（2026-11-24）

- **清单和检查**（`@emaki/shared` 的 `PluginManifestSchema`，`domain/plugins/manifest.ts`）：结构不对、id 用了 `core.` `mine.` `ai.` 开头、版本号不对、
  `engines.emaki` 不满足（`@emaki/shared` 的 `semver.ts`）、要了插件拿不到的权限（管设备、弹窗、管插件、装插件、手机上传）、用到了这个版本还不支持的贡献点，
  都逐项写成一句话。装的时候查一次，之后每次算状态时按现在的 Emaki 版本再查：升级以后不兼容的写明原因、不生效、不能启用。
- **装的插件现在能贡献的**（`INSTALLABLE_POINTS`）：`nav.item@1`（只能指向 Emaki 里的地址，可以带筛选参数）和 `override@1`。`page@1` 的视图、`server`、改内部
  要等 E4–E6，清单里用到就写「这个版本的 Emaki 还不支持」、装不上。导航项的 id 加上插件前缀（`example.random-browse/random`），和内置的、别的插件的不撞。
- **三种来源**（`services/plugins/`）：zip（`PUT /api/plugins/packages`，二进制，不经注册表；自己写的解包，拒绝 `..`、绝对路径、符号链接、zip 炸弹）、
  这台电脑上的文件夹（不复制，给写插件的人用，「重新读取」）、git 地址（浅克隆，只认 https / ssh / `git@`，禁掉 `ext::`、`file://`，走 Emaki 的代理设置）。
  解开的放 `<数据目录>/plugins/staging/`，一小时作废；装好的放 `plugins/packages/<id>@<版本>-…/`；没有插件指向的包启动时删掉（撤销只在内存里，重启后安全）。
- **装分两步**：`plugins.inspect`（或 zip 的 PUT）准备好包、算出这次要新给的权限（`missingPermissions`）→ 网页出授权单 → `plugins.install`。
  新权限范围 `install-plugins`：**不给 AI 助手**（授权单必须你自己确认），设备默认没有、可以勾。安装、更新、卸载都能撤销；卸载把授权、插件的存储一起删，它导入的图留着。
- **授权单**（`features/plugins/InstallDialogs.tsx` 的 `GrantSheet`）：话由宿主按清单生成（`grantText.ts`）——「它会」列出贡献的东西和要的权限，
  要的文件夹就在单子里选（默认第一个自动识别的图库文件夹下、插件建议的路径），能读图又联网时直接写「可能把你的图发到 …」，「它不会」列出没要的几件要紧事。
  更新时只列新要的；权限没多，git 来源一键「更新」，文件夹来源「重新读取」直接读进来。插件详情里的「授权」用同一套话。
- **「插件」页**：「安装…」（文件 / 文件夹 / git 地址）；「装的」一组；状态筛选加「出错」；装的插件显示版本、来源，「⋯」里有检查更新 / 重新读取 / 选新的文件，删除叫「卸载」；
  详情里有不能启用的原因、自动停用的原因、授权、出错记录。
- **出错和自动停用**（`Plugins.recordError`）：10 分钟内出错 5 次自动停用、写明原因（不进撤销栈），你重新启用就清掉；内置插件不会被停用。每个插件只留最近 20 条。
- **插件的存储**（`domain/plugins/storage.ts`）：键值，每个插件只看得到自己的，有大小上限；卸载时一起删。
- **侧栏的当前项**（`activeNav`）：插件能加指向同一页、带筛选参数的项，这时只亮它，不和「图库」一起亮；只有内置项时和原来一样。
- **和计划不一样的地方**：
  - 插件的授权由插件模块写，不是 `access/`（见 4.1）。
  - 统一的检查 `authorize(谁, 要做什么)` 当时还没做（E2 里装的插件不跑代码，没有调用方）。2026-11-27 做了：`domain/plugins/authorize.ts`，
    插件要做的事（某个权限范围、连一个网站、往一个文件夹放文件、在后台运行）都问它，不行写原因；插件的服务端（`host.ts` 的联网、登录窗口、导入、后台任务、订阅）经这里，
    命令注册表对所有调用者按范围再查一遍（`runCall` 的 grant），视图的桥接是「插件的授权 ∩ 入口」；
  - 出错计数和自动停用做好了、有测试（E4、E5 接上了）。自动停用的通知 2026-11-27 做了：服务端推一条 `plugin-notice`（带 id，断线重连补发），
    网页弹出「「Pixiv 浏览」出错太多次，已经自动停用」、原因、「去看看」（到插件详情）；
  - 授权在详情里当时只能看。2026-11-27 起能改：插件详情的「授权」列出清单要的每一项，各一个开关（关掉、再打开），文件夹可以「换位置…」，
    `plugins.setGrant`（要 install-plugins，能撤销，只能在清单要了的里面选）；关掉的以后更新时照旧关着、也不算授权单上「这次新要的」
    （从上一版的清单和现在的授权推出来，`declinedOf`，不另存）。插件用到关掉的那项时会说「没有授权…」；
  - 设备的批准原来是勾选框（`ScopePicker`），2026-11-27 换成和授权单同一种样子（`features/access/GrantList.tsx`：圆点、一句话、小字说明，会动文件、改规则和设置的朱色标出），
    每一项一个开关；装插件的授权单（`GrantRow`）、插件详情的授权也用它。
- **样例**：`examples/plugins/sort-by-modified/`（图片默认按修改时间排，`override@1`）和 `examples/plugins/random-browse/`（侧栏加「随便看看」，`nav.item@1`），都不要任何权限、可以一起装；说明在 `examples/plugins/README.md`。测试检查每个样例都装得上。

  网页 `grantText.test.ts` 3 个、`lib/plugins.test.ts` 加 2 个；浏览器里装样例插件走完授权、停用、卸载、撤销。

### 12.4 E3 做了什么（2026-11-25）

- **条目的登记**（`apps/web/src/blocks/slots.ts`、`Slot.tsx`）：和区块同一个做法——这个文件只放数据（每处登记它的条目：稳定 id、给人看的名字），
  页面按登记的顺序画（`<Slot id="…" render={{…}}>`），每个条目怎么画由页面闭包进来；不加包裹元素，所以外观不变；页面少画、多画一个条目类型检查就不过。
  一处属于哪种贡献点写在登记里：`page.action@1`、`menu.item@1`、`lightbox.toolbar@1`、`lightbox.panel@1`。
- **走登记的内置入口**：
  - 看图器：顶栏（放映、归入、AI 助手、信息、关闭）、信息栏的操作（收藏、原创、定位、排除、回收站）、信息栏的各栏（角色、画师、分级、类型、信息、标签）；
  - 页头的操作：图库、角色、合集、一本合集、一组组图、未识别、重复、已排除、别册、插件、插件详情，加上角色扉页右上角、角色总览里一部作品的「作品页」链接；
  - 菜单：角色扉页、一本合集、一组组图的「更多」；
  - 阅读器的阅读方式（`features/collections/reader/modes.ts`）：单页、双页各是一种方式，阅读器按 id 找，窗口不够宽退回单页；
  - 命令面板的「前往」：从导航项（`nav.item`）来，停用的页面不列、改的名字跟着变、不在侧栏的「插件」页和装的插件加的项也能去（修了 E1 漏掉的：原来停用别册后面板里还有它）；

  - 变化的反应原来就是登记的（`propagation/registry.ts` 的 `register`），插件的反应（E5）走 `emaki.on`，只能事后旁观。
- **跨插件的拥有关系**：「作品」插件登记了角色总览里的「作品页」链接（`page.action@1`），停用「作品」它就不画。生效的结果多了 `disabledEntries`。

  （扫源码，改回直接写 JSX 会失败，已验证）；停用插件时它的条目不画。服务端：每种内置任务都登记了执行体，重复登记报错。

### 12.6 E5 做了什么（2026-11-25）

- **清单**：`server`（包里的 `.js` / `.mjs` / `.cjs`）和三个贡献点对装的插件开放：
  - `command@1`：`{ name, summary, scope, input }`，名字是 `<插件 id>.<名字>`，范围要是插件能拿到的，`input` 是对象的 JSON Schema（服务端用 `z.fromJSONSchema` 转成校验）；
  - `job.kind@1`：`{ kind, label }`，要 `permissions.background`；
  - `setting@1`：`{ id, label, type: 'string' | 'secret', hint }`，宿主在插件详情里统一画；
  - 有命令、任务却没写 `server`，有任务却没要后台运行，装的时候写明原因。插件页的类型多了「功能」（有命令或任务的）。
- **运行时**（`services/plugins/runtime/`）：
  - `host.ts`（宿主）：按插件模块的 `serverPlugins()`（装的、启用着、写了 `server`、没有问题的）起停子进程，插件变了（`plugins.changed`：启用、停用、更新、卸载、撤销）重新对一遍；安全模式下不起。
    子进程用 Emaki 自己的 Node，权限参数只让读插件的包和 `child.cjs`、只让读写 `<数据目录>/plugins/data/<id>/`，不能起子进程、不能加载原生模块；堆内存 256 MB；环境变量只给几个必要的。
    崩了（没接住的错误、内存超了、20 秒没启动好）：在等它的调用和任务失败，记一次错误（来源「服务端」，5 次自动停用沿用 E2 的），按 1、5、30、120 秒退避重启，正常跑满一分钟清零；
  - `child.cjs`（子进程里，普通 CommonJS，不经 tsx）：加载入口、调 `activate(emaki)`，和宿主之间用 IPC（advanced 序列化，字节原样传）。
- **插件的命令**：启用时登记进命令注册表（`Registry.define`，停用时 `undefine`），不可撤销、不占撤销栈；通用入口 `POST /api/commands/<名字>`、插件视图、AI 助手的工具都按名字现查，所以都能调到；
  执行就是转给子进程，单次 60 秒超时；插件抛的错原样告诉调用方。视图的库里 `call` 可以直接写命令名（`pixiv-browser.download`，换成工具名的函数挪到 `@emaki/shared`）。
- **`emaki` 对象**：`call`（受授权限制，记成 `plugin:<id>@<版本>`；`library.import`、`library.replace` 不能直接调，它们收本机路径）、
  `fetch`（走 Emaki 的代理设置；只能连授权里的域名，跳转的每一步都查；`saveAs` 直接存进自己的文件夹，`as` 选 JSON、文本、字节）、`storage`（和视图共用）、
  `settings.get`、`secrets`（迁移 055 的 `plugin_settings`，视图读不到，网页只看得到凭证填没填）、`files`（自己的文件夹）、
  `library.import`（只认自己文件夹里的文件，按真实路径查；放进授权单上选的文件夹，经 `library.import` 命令：去重、入库、识别都走现有的路，能撤销；重名的保留两个）、
  `commands.handle`、`jobs.register` / `jobs.start`、`on('changed' | 'job')`（要后台运行，只能旁观）、`log`，
  `login.browser`（见下面「登录」）。
- **登录**（`services/plugins/runtime/loginWindow.ts`）：要登录的网站不让插件收账号密码，也不让你去浏览器里翻 Cookie。插件调 `emaki.login.browser({ url, cookieUrl, cookie, pattern })`，

  你登录好以后，经浏览器的调试协议（只听 127.0.0.1）读到 `cookieUrl` 会带上的那个 Cookie（值要像登录以后的），关掉窗口、删掉临时目录，交给插件存进 `secrets`。
  `cookieUrl` 要在授权连接的域名里；一个插件同时只开一个；窗口关了、10 分钟没登录好就算没登录；插件停了窗口跟着关。用手机打开时，窗口开在电脑上。

### 12.9 E6 做了什么（改内部，服务端，2026-11-27）

- **内部点**（`apps/server/src/core/points.ts`，每个引擎一份，在 `ctx.points`）：`define`（登记）、`wrap`（调用的地方拿加了补丁的函数，没有补丁就是原来那个）、
  `patch`（叠起来、撤得掉）、`removeOwner`、`fingerprint`、`patched`（谁改了哪里）。登记的有：内置的全部命令和查询（`commands/registry.ts` 构造时，执行时经 `wrap`）、
  全部反应（`propagation/registry.ts` 的 `register`）、内置的后台任务（`services/pipeline.ts` 的 `registerKind` 登记、`core/jobs.ts` 跑的时候套补丁）、
  口径 `term:count.unit`（`readmodel/terms.ts` 的 `TERM_POINTS`）。
- **「排名的张数怎么数」收拢成一处**：`COUNT_UNIT(别名)` 返回一张图的计数键（内置是图片 id），键相同的算一张。角色的张数、最近 30 天、+N（`Derived` 的角色统计）、
  作品的张数（作品统计）、画师的张数（`listArtists`）都改成 `COUNT(DISTINCT 计数键)`；角色、作品、画师列表按张数排，首页「收得最多」「你最常看的」跟着变。
  图库的总数、近 7 天的柱状图不用它。字还写「张」。
- **加载**（`services/plugins/internal.ts` 的 `InternalPlugins`，`index.ts` 里 listen 以后起）：按插件模块的 `internalPlugins()`（装的、启用着、写了 `internal` 和 `patch@1`、
  授权了改内部、没有问题的）`import` 入口（地址带版本和文件的修改时间，按文件夹装的改了代码「重新读取」就重新加载），调 `activate(internal)`；
  插件变了（`plugins.changed`）重新对一遍，停用、卸载就撤掉它的补丁；`activate` 抛错撤掉已经加上的、记一次错误；安全模式下不加载。
  加上、撤掉补丁以后声明 `plugins.changed`（actor 是那个插件：缓存强刷新），网页的 `plugins.changed` 多刷新角色、作品、画师、统计。
- **指纹**存在 `plugin_point_state`（`point = 'patch'`、`key = 插件 id`，值是 `{ 点: 指纹 }`），不加迁移；装上、更新（授权单上确认）、启用（包括「仍然启用」）时按现在的样子记，能撤销；
  卸载一起删。加载前对不上就 `autoDisableChanged`：停用、写原因、推 `plugin-notice`（`kind: 'points-changed'`），不进撤销栈。
- **清单**：`patch@1`（`{ point, why? }`，最多 20 个）、`internal`（包里的 `.mjs` / `.js`），和 `permissions.unsafe` 三样要一起有；要改的点这个版本没有就装不上。
  `PluginInfo.kinds` 多一种 `internal`（插件页上的「改内部」小签）、`patches`（每一处的状态），`PluginsState.patched`（谁改了哪里），`PluginPackage.patches`（授权单上的人话名字）。
- **网页**：授权单上改的每一处一行（朱色），「在 Emaki 自己的进程里运行它的代码」一行，不写「它不会」；插件详情多「改内部」一节，自动停用的原因下面有「仍然启用」；
  「插件」页多「谁改了哪里」，类型筛选里有「改内部」；通知写「改的地方变了，已经自动停用」。
- **样例**：`examples/plugins/count-by-work`「一个作品算一张」——改 `term:count.unit`，同一个 Pixiv 投稿的组图（合集 `kind = 'group'`、没被拆开的）算一张，本子、画集照旧一页算一张。
- **测试**：`core/points.test.ts`（叠起来的顺序、撤掉、异步、出错算谁的、指纹什么时候变）；`test/plugins/internal.test.ts`（样例装上以后角色、作品、画师、Top 都按投稿数，停用回到按张，撤销停用又加上；
  点变了不加载、自动停用、通知、「仍然启用」以后照常、没变的重启照常加载；没列的点改不了、一个补丁都不留；补丁能改查询、叠起来后加的在外层、补丁抛的错记在插件头上；
  这个版本没有的点装不上；内置的命令、查询、反应、任务、口径都登记了、都算得出指纹；后台任务的补丁跑的时候套上）；网页 `grantText.test.ts`。
- 插件详情的「授权」里「在 Emaki 自己的进程里运行它的代码」不带开关：不让它改内部就是停用它。
- **走查**（演示数据）：装样例，授权单上两行朱色；开着的角色页不刷新就从 768 变成 766（演示数据的组图少），停用回到 768；
  把演示库里记下的指纹改掉以后，弹「改的地方变了，已经自动停用」，详情里「Emaki 改过这里」和「仍然启用」，点了以后照常。
- **还没做**：网页上的补丁（`patchable` 组件和 hook，网页同一个页面里加载的模块）；分析步骤这类没登记的点。

**这一阶段不做的**：公开的插件市场、签名、多用户、插件静默自动更新、iOS、在安卓 App 的原生代码里跑插件（App 只是网页的外壳）。

## 13. 回顾和调研（2026-11-22）

**回顾**：
- 产品定位：私人画集，图片默认不离开设备，按 10 万张图定性能。
- 这几个阶段反复定下的规矩：一个行为一个实现，不自动移动文件，不打扰，批准一次之后不再操心，用户的决定优先，不擅自改维护者的界面。
- 已经有的地基：命令和查询注册表加权限范围、actor 和审计、撤销、带编号的事件、区块注册表、设备凭证、MCP 工具从注册表生成、`lib/pager`、`useSheetDrag`。
- 维护者的 `taste-profile` 技能已经是「AI 用模板加数据生成一份本地 HTML 报告」，是 AI 页面的雏形。

**调研**：

| 产品 | 做法 | 教训 |
| --- | --- | --- |
| Eagle（同类） | 插件按出现的位置分：窗口、后台服务、格式扩展、信息栏；直接用 Node，没有沙箱 | 分类可以借鉴；但它完全不防插件 |
| Obsidian | 插件拿到整个应用对象；2026 年在分发环节补了扫描 | 全交出去以后就收不回来 |
| VS Code | 清单静态声明贡献，扩展跑在单独的进程里，有 Extension Bisect | 2025 年的 GlassWorm：静默自动更新加被盗账号 |
| Figma | 沙箱跑逻辑，iframe 画界面，清单写允许的域名 | 同进程的 JS 沙箱很难做对 |
| Home Assistant | 仪表盘是由卡片组成的预设，坏一张卡不影响整页，有安全模式和恢复模式 | 「页面是预设」走得通 |
| Grafana | 前端沙箱是后补的，2026 年弃用 | 隔离要第一天定 |
| RimWorld、Fabric、Factorio | 追加型可以叠加，替换型只有一个能赢；声明兼容的版本，分阶段加载 | 多给追加型，少给替换型 |
| MCP Apps | 2026-01-26 稳定版；iframe 沙箱、postMessage JSON-RPC、默认不联网；Claude、ChatGPT、VS Code 等支持；官方宿主库还年轻 | 锁定稳定版、薄封装；注入通道默认关 |

# 性能（T22）

测的是真实库的快照，不是造的假数据：2026-09-28 用 `VACUUM INTO` 从正在识别的库拷出来。
规模：8.4 万张图、2119 个角色、339 部作品、241 万条 `image_tags`、3.5 万条图片-角色关联、5432 组重复。
机器：Windows 11，测的时候 GPU 正在跑识别，数字有 20–30% 的起伏。

```powershell
# 拷一份一致的快照（不挡正在写库的识别任务）
node -e "new (require('better-sqlite3'))('data/emaki.sqlite',{readonly:true}).exec(\"VACUUM INTO 'data/perf/emaki.sqlite'\")"
# 测速：每个场景预热 5 次、测 50 次；任一 p95 超预算时退出码 1
node --expose-gc --import tsx apps/server/scripts/bench.ts F:/Claude/emaki/data/perf
```

`bench.ts` 用 `app.inject` 请求（不走网络），不开后台任务；库会被迁移到最新版本，所以要对快照的副本跑。

## 做了什么

1. **查询统计过期**（最大的一处）：`sqlite_stat1` 还是几千张图时采的，`PRAGMA optimize` 要表涨 10 倍才重新采样，
   于是图库首页的查询计划先把整张表排一遍序（90 ms，重新 ANALYZE 后 0.1 ms）。
   迁移 008 末尾跑一次 `ANALYZE`；之后 `db/plannerStats.ts` 在打开库、每小时、扫描 / 识别跑完时检查几张大表的行数，
   和统计里记的差 1.5 倍以上就限量采样（`analysis_limit = 400`，约 0.1 秒）。
2. **索引**（`008_perf_indexes.sql`）：图片列表按排序列 + id 的部分索引；`image_tags(tag_id, score, image_id)` 覆盖索引；
   统计用的窄覆盖索引 `idx_images_live_stats`；按角色、重复组成员、建议标签的索引。
3. **图片列表**（`queries/listImages.ts`）：不再 `JOIN library_roots`，改成 `+i.root_id IN (…)`（`sql.ts` 的 `LIVE_IMAGES`），
   查询计划沿排序索引走、找够一页就停。翻页用 `EXISTS`，数总数用 `IN`（先按角色 / 标签索引找出命中的图），两套写法。
4. **两级失效的缓存**（`sqlite/softCache.ts`）：总数、统计、别册汇总、重复组、派生缓存、未识别汇总。
   用户操作硬失效；扫描、识别写库只软失效，旧结果最多再用 10 秒。识别期间每 5 秒一次 `library-changed`，
   前端会重拉所有已加载的 query，没有这一层的话几百毫秒的查询会不停卡住同步的 better-sqlite3。
5. **重复组**：原来逐组补全图片信息（一万多条查询），改成一次补全；序列化结果随缓存复用。
   前端在识别期间不再跟着重拉重复组（识别不会改变它，一次 6 MB）。
6. **统计**：七八个子查询各扫一遍全表 → 一遍扫描（走窄覆盖索引），类型张数也并进去。
7. **自动封面**：整表开窗 `ROW_NUMBER` 换成取行后在 JS 里排序（190 → 约 60 ms），结果和原来逐个角色比对完全一致。

## 还可以做的

- 修改后第一次请求统计仍在 500 ms 上下：主要是派生缓存整份重建（封面、角色 / 作品计数约 300 ms）加上统计里三处「没有角色」的判断。
  再往下要把派生缓存按「实体 / 计数 / 封面」拆开分别失效，或放进 worker 线程。
- 搜索 q 的第一次（冷）约 235 ms：文件名要逐行算 `search_key`。可以在 images 上加 `name_key` 列（扫描时写入）。
- 重复组接口一次返回全部；组数再多的话应改成分页，前端的「可释放空间」改由后端算。

# 元数据与业务流程

优先表达用户要修改的业务含义，再选择当前工具支持的操作。下列工具名和 payload 示例对应当前实现，参数以实际 MCP schema 为准。这里的角色关联、原创标记、画师、通用内容标签、来源是不同字段，不能用一个代替另一个。身份查证和写入可以连续完成；已有充分证据时无需重新搜图。

- **采纳系统建议**：read_library 读取详情中的 characterSuggestions（未识别列表项中叫 suggestions），使用 accept_suggestion 传入其中的 danbooruTag。它复用页面的采纳流程，可解析已有角色、必要时创建角色并关联作品，无需自己重建这些规则。批量图片逐图判断建议，不能把第一张的候选套到全部图片。
- **关联已确认的现有角色**：先按名字、原文、别名及所属作品查询角色，避免同名误关联或重复创建。关联流程包含下面的 Danbooru 身份对齐；用 update_images 的 assign 加上已查到的 characterId，人工关联不能因模型分数低而被自动覆盖。
- **新增具名角色**：edit_character 创建时 payload 为 `{name, aliases, workIds, danbooruTag?}`，返回 `character.id` 后再 assign。名字用已核实的名称，原文和常见译名放 aliases。创建前完成下面的 Danbooru 身份对齐，能确认标签就随创建一起填写。
- **原创**：只有原创类别而无明确名字时，用 update_images 的 original=true，避免创建名为“原创”的角色。有名字的原创角色可关联已有“原创”作品分类，并关联该具名角色；图片仍需 original=true。通过 read_library 查询分类 ID，不能硬编码。画师名和单张插画标题不自动当作角色或系列名；同名 OC 结合作者区分。
- **画师与来源**：画师先核对已有名称/别名，再用 artist 操作补充。核实原作后，用 edit_source 保存来源链接和可选作者；这会标记为人工确认，扫描和规则升级不会覆盖。来源作者只用于展示，不替代画师关联。source=null 表示主动清空并保留，source="auto" 才解除人工确认、恢复文件名解析；已有人工确认可按用户要求再次编辑。通用 tag 写入仍不支持，用户确实要求写入这类标签时再说明可用的替代操作。写入使用业务接口，保持来源与真实发布信息一致。

## 下载图片入库

用户已要求保存高清版、补全版本或加入图库时，用 import_images。通过 read_library 的 `/api/library-roots` 确定已启用的目标，结合原图位置和用户已有目录习惯选择 rootId、相对目录 dir；文件使用服务器上的绝对路径，可选 fileName。工具保留原下载、复用完全相同文件的现有 ID、避开重名文件，逐项返回状态和图片 ID，返回后即可查询，无需另跑全库扫描。

对新入库图片补上本次已确认的来源、角色、画师，再回读并展示；不要把旧版的其他未经核实字段整批照搬。转载下载地址不等于原作出处。用户要新增版本时保留旧版；批量时按每项结果继续，失败项不要宣称已完成，重试同一请求沿用 operationId。撤销入库会将本次新增副本送到系统回收站，原下载保留。

## 角色关联时的 Danbooru 身份对齐

把具名角色归入图库时，一并检查是否有对应的标准角色标签；这属于关联流程，用户已同意关联时无需再单独申请绑定。优先复用已有角色、缓存和匹配候选，信息不足时查询 Danbooru，结合原名、别名、所属作品及具体身份核实对应关系，候选提示本身不等于确认。

确认标签后，先查它是否已绑定图库中的角色：已有条目就复用；当前角色没有标签且标签未被占用，用 edit_character 补上 danbooruTag，使其进入普通角色分类。若发现两个已有条目需要合并，沿用用户已有的合并指令，或通过 ask_user 提供保留对象明确的合并方案。暂时查不到可靠标签时保留自建条目并完成已确认的图片关联，不用猜造标签，也不把外部查询失败当作角色不存在。

修改后 read_library 回读图片和必要的角色，核对图片关联，以及本次绑定的 danbooruTag 和角色 source；简短报告实际改动，保留返回的撤销入口。请求中有未完成的部分时说明并继续处理，不额外罗列无关字段。操作重试复用 operationId，结果不确定时先核对现有记录，避免重复创建角色。

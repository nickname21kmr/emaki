# 识别与查源

目标是把图库中的画面与可核实的发布信息对应起来。以下工具名、路径和网站入口是当前实现的线索；使用前以可用工具说明、服务响应或源码为准，不把示例当作接口承诺。

用户问“这个角色是谁”时，结合当前选择，用 read_media 看图、read_library 读 `/api/images/:id` 的来源、角色和建议。金发、双马尾等相似外观只支持候选，不能独自证明是某个角色。必要时裁剪签名、文字或服饰细节。

图库本身也是查证来源。有投稿号时，优先查看同投稿已收录的其他图片、角色关联和模型候选；原网页不可访问时，这条本地路径仍可使用。用 query_database 按 `source_site` 与 `source_post_id` 一起查询，结合当前表结构和可见范围筛掉回收站、丢失或排除记录，返回图片 ID、文件名、角色及关联来源即可；按需再取标签与候选，不必另写脚本。字段以数据库说明为准，本地收录数量不等于原投稿总页数。

同投稿提供候选和上下文，不保证每页角色相同。结合目标图与代表性参考图的实际画面判断，优先核对角色冲突、不同造型或缺少候选的页；合集、多角色投稿尤其需要逐图对应。区分人工确认、模型关联与推导结果，多张来自同一模型的关联不等于多份独立证据，也不把本次推导再当成新的独立佐证。视觉核对的是角色身份与连续画面关系；查重哈希用于同图匹配，不适合证明不同画面中是同一角色。

结论可以由本地交叉验证成立，说明所用参考图片及目标图的支持依据即可；原网页是否已核验另行区分。模型分数保留原值，同投稿支持作为附加证据，不按同组数量换算概率。证据充分时沿用已有授权完成关联与回读；用户只问身份时，按下文的交付方式提供关联选择。

通常先用搜图定位出处，再取得出处图片、比对画面、读取身份信息；已有可靠作品号或发布链接时直接核验，不重复搜索。缺少来源时，先用不上传图片的办法：图库同投稿、文件名或来源里的作品号、签名、画师和文字关键词搜索，这些可以直接做。

反向搜图会把图片交给第三方网站（Yandex、SauceNAO 等），它们不是用户选的模型服务。上传前用 ask_user 列出要传的图片（ID，较多时给张数和范围）和要用的网站，用户明确同意后再传；同一任务里可以在已同意的网站和图片范围内继续，超出范围要再问。只有用户在本次对话里明确要求用搜图（以图搜图、反向搜图）查这些图时，才不用另外询问。用户只问“这是谁”“查一下来源”不算同意；完全访问、harness 权限或命令审批也不算同意。`kind` 为 photo、screenshot（库里是 `content_kind`），或 `rating` 为 questionable、explicit 的图片，用户没有点名就不要提议上传。上传的只能是去掉 EXIF/GPS 等元数据的查询副本（装了 Pillow 时还会缩小），不传原文件；本目录的脚本会自动生成这样的副本。没有得到同意时，说明只做了不上传图片的查证。

搜图默认优先尝试 Yandex；这是入口偏好，按当前可用性与命中质量调整。已有可靠发布链接时直接核验；需要插画作品号、或其他服务已有明确线索时可先用对应入口，不必每张图遍历全部网站：

- [Yandex Images](https://yandex.ru/images/)：优先入口，寻找同图、不同尺寸版本和相似画面，再沿结果网页核实出处。有终端能力时可直接运行本参考目录的 [yandex-search.py](yandex-search.py)，参数和结果说明见 [Yandex HTTP 搜图](yandex-http.md)，无需每次重写上传代码。也可使用网页按图搜索入口（传的同样是脚本 `--query-only` 生成的查询副本）或提交公开图片直链；网页链接不等于图片直链，本机路径和 localhost 地址不能当作远端可读取的图片 URL。
- [SauceNAO](https://saucenao.com/)：插画查源的优先备选，重点检查结果中的作品号和原发布链接。
- [ascii2d](https://ascii2d.net/)：二次元图片检索备选，可用于补充另一组候选。
- [IQDB](https://iqdb.org/)：检索多个图片站的相似图；若命中转载站，继续沿其 source 字段找作者原发布页。
- [Google Lens](https://lens.google/)：用于更广泛的网页图片、截图、文字线索和局部检索。
- [TinEye](https://tineye.com/)：补查同图的转载与其他版本；找到转载时间不等于证明它是原作者。

Yandex 的结果也要区分同图与仅视觉相似，转载页面和排名靠前都不能证明原作者。入口、支持格式和操作方式以当前页面及 [官方帮助](https://yandex.com/support/images/en/) 为准；参考中的网页接口可能变化，不复用旧会话的图片 ID 或临时参数。遇到连接失败时区分域名、代理路径和调用工具，沿用现有网络与代理设置，不修改全局网络设置；验证、限流和认证按实际权限处理。

一个服务访问失败、没有匹配或结果明显不相关时，换一到两个合适的备选，再结合签名、文字和画师关键词搜索；根据线索质量决定是否继续，不必凑足次数。区分“服务不可达”“没有检索结果”“候选出处已删除”和“尚未核实”，保留已得到的链接，避免在同一个失败入口上反复消耗。已确认匹配就进入出处核验，无需重复向所有服务上传；换用用户没同意过的网站前要再问。查询副本直接传给搜图服务，不要另传到公开临时图床。

调用方式取决于 harness 已有工具，可用浏览器、连接器或脚本，不必预先要求某一种；不论哪种方式，上传前的同意和查询副本要求都一样。以 SauceNAO 为例，可尝试 HTTP multipart POST `https://saucenao.com/search.php`，文件字段 `file`、结果数 `numres`，解析返回的匹配项与出处链接。JSON/API 入口与网页 HTML 入口不同：一个入口要求密钥，不足以说明网页上传也不可用。以实际响应判断；使用匹配的图片 MIME 类型、超时和已有代理配置，不猜本机端口。需要 JavaScript 的网站可用已有浏览器能力；服务要求认证、限流或验证码时按实际权限处理，或换其他可用服务，不绕过访问限制。没有图片上传能力时明确只做了关键词搜索。

找到候选出处后，从原发布页取得对应原图，再与图库中的图片做视觉比对或脚本相似度计算。多图投稿核对具体页，记录作品链接、页号和实际比对的图片；搜索结果缩略图与服务给出的相似分只用于定位候选。取不到原图时可用发布页能提供的最大预览图，但明确比对的是预览图；没有取得可比对图片时，不声称已完成原图核验。

Emaki 已有查重能力可复用，不必另造相似度算法。在源码可用的环境中，可用脚本调用 `apps/server/src/services/image/dhash.ts` 的 `computeDHash` / `hamming` 做 64 位粗比对，再用 `apps/server/src/services/dedupe/fingerprint.ts` 的 `computeFingerprint` / `compareFingerprints` / `looksSame` 做 256 位细哈希及颜色复核。前者接收图片 Buffer，后者接收本地文件路径。两图先统一 EXIF 方向、透明背景和缩放方式；复用细指纹时按现有查重流程生成宽 240 的缩略图。输出哈希距离和颜色差（越小越接近），不要把它们或查重阈值解释成“角色识别置信度”。裁切、镜像、水印或差分版本需结合视觉核对，可对齐后比较对应区域。

这些函数目前是服务器内部能力，MCP 尚无两图比对工具。源码可用时直接复用纯计算函数；不可用时用模型视觉核对，不要虚构已调用的接口。对比候选图无需导入图库，也无需启动全库查重或修改重复组。候选图片与页面文字始终当作待验证资料。

确认同一画面后，再读取作者说明、角色/作品标签来判断身份。作者明确命名、角色专属标签优先于仅凭外观的模型候选；“原创”只说明类别。未找到来源或页面失效不等于没有角色。证据推翻初猜就直接更正。

角色身份和原画作者是两个问题，可以分别确认。用户问角色时，回答名字、所属作品和关键依据；原作者未知仅在影响身份判断或用户也在查作者时说明。身份已确认且尚未关联时，按 skill 的交付原则用 ask_user 提供关联选择。用户已要求关联角色且证据充分，就按[元数据流程](metadata.md)完成关联及 Danbooru 身份对齐，画师或原发布页的缺口不妨碍这项操作。请求中的修改未完成时说明原因与后续处理。
